01Foundation

Arrays & Hashing

Trade memory for speed.

Finding something in a list means checking every item. A dict or set is a magic drawer: you ask “do I already have this?” and it answers in one step, no matter how much is inside. So instead of looking backwards over everything you have already seen, you write each item down as you pass it.

You reach for it when

  • “have I seen this before?”
  • counting how often something appears
  • find the pair / the duplicate
  • group things that share a key

The trap

Dict keys must be hashable. A list cannot be a key, a tuple can — which is exactly why Group Anagrams keys on tuple(sorted(word)) instead of the sorted list.

The move O(n) time · O(n) space

seen = {}                          # value -> where we saw it
for i, x in enumerate(nums):
    if target - x in seen:         # one step, not a scan
        return [seen[target - x], i]
    seen[x] = i                    # write it down and move on

Where this lives in real code

Deduping events in an ingestion job. A set of event_ids answers “already processed?” in O(1) instead of re-scanning a list per row. A Redis SET in front of a database and a Bloom filter are the same bet at a bigger scale: spend memory, stop repeating work.

02Foundation

Two Pointers

Two fingers, closing in.

Checking every pair costs n×n. Put one finger at each end of a sorted array instead. The sum is too small? The only way to grow it is to move the left finger up. Too big? Move the right one down. Each step throws away a whole group of pairs at once, so one pass is enough.

You reach for it when

  • the input is sorted, or you may sort it
  • find a pair that adds up to something
  • palindrome / mirror checks
  • do it in place, no extra memory

The trap

In 3Sum you must skip duplicate values after moving a pointer, or the same triplet comes out twice.

The move O(n) after the sort · O(1) extra space

l, r = 0, len(nums) - 1
while l < r:
    s = nums[l] + nums[r]
    if s == target:
        return [l, r]
    if s < target:
        l += 1                     # need bigger  -> left finger up
    else:
        r -= 1                     # need smaller -> right finger down

Where this lives in real code

Merging two already-sorted partition files without loading either into memory: one cursor per file, always advance whichever value is smaller. That is the merge step in merge-sort, and the core of every sort-merge join a query engine runs.

03Foundation

Stack

Last in, first out.

A stack of plates: you add to the top and take from the top. That is exactly right whenever the most recent thing you saw is the one you must deal with first — the innermost bracket, the last undo, the nearest unresolved item. Anything that nests wants a stack.

You reach for it when

  • brackets, nesting, undo
  • “next greater / warmer / taller”
  • evaluate an expression
  • you need the most recent unfinished thing

The trap

Popping an empty stack. Check if not stack before you pop, every single time.

The move O(n) time · O(n) space

pairs = {")": "(", "]": "[", "}": "{"}
stack = []
for ch in s:
    if ch in "([{":
        stack.append(ch)                     # remember the open one
    elif not stack or stack.pop() != pairs[ch]:
        return False                         # newest open must match
return not stack                             # nothing left dangling

Where this lives in real code

Every JSON and XML parser is this loop, and so is the call stack your own program runs on. In data work, a monotonic stack answers “how many days until a higher price?” across a whole time series in one pass instead of n².

04Foundation

Binary Search

A million items in twenty questions.

Guess a number between 1 and 100. Say 50. Too high? Now it is 1–49 — half the world just disappeared from one question. Repeat. Doubling the input only adds one more step, which is why this stays fast when everything else stops being fast.

You reach for it when

  • sorted input
  • “smallest value that still works”
  • a huge range with a yes/no test
  • the required time is O(log n)

The trap

Off-by-one infinite loops. Pick one template — while l <= r with mid + 1 and mid - 1 — and never improvise a variation under pressure.

The move O(log n) time · O(1) space

l, r = 0, len(nums) - 1
while l <= r:
    mid = (l + r) // 2
    if nums[mid] == target:
        return mid
    if nums[mid] < target:
        l = mid + 1                # answer lies to the right
    else:
        r = mid - 1                # answer lies to the left
return -1

Where this lives in real code

Tuning a batch size or worker count where “does this config stay under the memory ceiling?” is a monotonic yes/no — binary search the parameter instead of testing every value. It is also how a database seeks inside a sorted index page.

05Foundation

Sliding Window

Never restart from the beginning.

Look at the list through a window. Slide the right edge to take one more item in. The moment the window breaks the rule, slide the left edge forward and drop items until it is legal again. Both edges only ever move right, so the whole array is covered in one pass.

You reach for it when

  • longest / shortest run that satisfies a rule
  • the word contiguous or substring
  • “at most K of something”
  • a fixed-size chunk moving along

The trap

Shrinking with if instead of while. One shrink is often not enough to make the window legal again.

The move O(n) time — each index enters and leaves once

from collections import defaultdict

l, best, window = 0, 0, defaultdict(int)
for r, x in enumerate(nums):
    window[x] += 1                          # grow on the right
    while window[x] > 1:                    # while ILLEGAL, not if
        window[nums[l]] -= 1
        l += 1                              # give back on the left
    best = max(best, r - l + 1)

Where this lives in real code

A rate limiter is literally this: “at most 100 requests in any 60 seconds” is a window over timestamps. Rolling 7-day averages in a streaming job (Kafka Streams, Flink) are the same shape with time as the edge instead of an index.

06Foundation

Linked List

Every box knows only the next box.

A treasure hunt: each note tells you where the next note is. You cannot jump straight to note five — you have to walk. In exchange, you can slip a new note into the middle without moving any of the others. Almost every question here is careful pointer surgery, done in a fixed order.

You reach for it when

  • reverse a list or part of one
  • find the middle / detect a cycle
  • merge two sorted lists
  • O(1) insert and remove is required

The trap

Overwriting curr.next before saving it — the rest of the list is unreachable and gone. Also: a dummy head node removes every special case around the first element. Use one.

The move O(n) time · O(1) space

prev, curr = None, head
while curr:
    nxt = curr.next        # 1. save the rest of the chain
    curr.next = prev       # 2. flip this link backwards
    prev = curr            # 3. shuffle both pointers along
    curr = nxt
return prev                # prev is the new head

Where this lives in real code

An LRU cache is a hash map plus a doubly linked list: the least recently used item sits at one end, so eviction is O(1). Your OS page cache, Redis, and functools.lru_cache all lean on that shape.

Trees

Solve the small version, let recursion do the rest.

A family tree where everyone has at most two children. To find how deep the tree goes, do not try to picture the whole thing. Ask your left child “how deep are you?”, ask your right child the same, take the bigger answer and add one for yourself. Every node runs that exact same tiny rule.

Tries

A tree of letters, prefixes stored once.

Think of your phone contacts. Type Ma and it instantly offers Mahmood, Maria, Mark. Every name that starts the same way walks the same first steps, so the trie stores that shared beginning one time and branches only where the words actually differ.

You reach for it when

  • the word prefix appears
  • autocomplete / spell-check
  • a dictionary of words searched many times
  • wildcard search across a word list

The trap

Forgetting the end flag. Without it, "ca" looks like a stored word just because "cat" was inserted.

The move O(len(word)) per insert or lookup — the dictionary size does not matter

class Trie:
    def __init__(self):
        self.children = {}                 # letter -> next node
        self.end = False                   # a whole word finishes here

    def insert(self, word):
        node = self
        for ch in word:
            node = node.children.setdefault(ch, Trie())
        node.end = True                    # do not forget this line

    def starts_with(self, prefix):
        node = self
        for ch in prefix:
            if ch not in node.children:
                return False
            node = node.children[ch]
        return True

Always hands you the smallest thing first.

A hospital waiting room. People arrive in any order, but the most urgent one is always called next, and nobody re-sorts the whole room to make that happen. A heap keeps just enough order to know its extreme — which is all you ever need for “top K” or “next cheapest”.

heap = []                          # Python heaps are MIN-heaps, always

Backtracking

Try it. If it fails, undo the move.

Walking a maze. Go down a path. Dead end? Walk back to the last fork, rub out your footprints, and take the other path. That rubbing-out is the entire trick — it is one line of code, and it is what lets you reuse the same list for every attempt instead of copying it a million times.

You reach for it when

  • all subsets / permutations / combinations
  • “find every valid way to…”
  • brute force, but with rules that let you quit early
  • sudoku, N-Queens, word search on a grid

The trap

res.append(path) without [:]. You stored a reference, so every answer in res ends up identical — usually all empty.

The move Exponential by nature — pruning early is the only real optimisation

res, path = [], []

def backtrack(start):
    res.append(path[:])                 # [:] copies — path keeps mutating
    for i in range(start, len(nums)):
        path.append(nums[i])            # 1. choose
        backtrack(i + 1)                # 2. explore
        path.pop()                      # 3. UN-choose  <- the magic line

backtrack(0)
return res

Where this lives in real code

A query planner trying join orders and abandoning a plan the second its cost estimate passes the best one found so far. Hyperparameter search with early stopping is the same loop: explore, measure, prune, step back.

1-D Dynamic Programming

Recursion that stopped repeating itself.

To reach stair 10 you arrived from stair 9 or stair 8. So ways(10) = ways(9) + ways(8). Plain recursion recomputes ways(5) hundreds of times over. DP writes each answer in a row of boxes the first time it is needed, then just reads it. Same idea, same recurrence — you only stopped throwing work away.

You reach for it when

  • “how many ways…”
  • max or min over a sequence of choices
  • your recursion works but times out
  • the answer at step i depends on a few earlier steps

The trap

Wrong base cases, or looping in a direction that reads dp[i-1] before it was filled. Write the recurrence out as an English sentence before you write any code.

The move O(n) time · O(n) space, often reducible to O(1)

dp = [0] * (n + 1)
dp[0], dp[1] = 1, 1                 # base cases you know for free
for i in range(2, n + 1):
    dp[i] = dp[i - 1] + dp[i - 2]   # the recurrence, in one line
return dp[n]

# only ever look back two cells? then two variables replace
# the whole array and the space drops to O(1)

Intervals

Sort by start, then only look at the last one you kept.

Meetings in a calendar. Line them up by start time. If the next meeting begins before the one you are holding ends, they overlap — stretch your block to cover both. If it begins after, there is a gap, so close that block and start a new one. Sorting is nearly the whole solution.

You reach for it when

  • the input is pairs of [start, end]
  • merge / insert / count overlaps
  • meeting rooms, bookings, schedules
  • “remove the fewest to make them disjoint”

The trap

Whether touching intervals like [1,2] and [2,3] count as overlapping is decided by the problem statement, not by you — read it. And for “remove the fewest”, sort by end time, not start.

The move O(n log n) for the sort, then one linear pass

intervals.sort(key=lambda x: x[0])       # sorting by START is the trick

    if start <= merged[-1][1]:           # touches the block we are building
        merged[-1][1] = max(merged[-1][1], end)
    else:
        merged.append([start, end])      # a real gap -> new block
return merged

Greedy

Take the best move now and never look back.

Making change: grab the biggest coin that still fits, repeat. Fast, simple, and correct — for normal coins. For a strange set of coins it quietly gives the wrong answer. That is the whole personality of greedy: brilliant when the local choice is provably safe, wrong when it is not.

You reach for it when

  • a local rule that obviously cannot hurt you
  • max / min with an ordering you can exploit
  • you can explain in one sentence why the greedy choice is safe
  • if you cannot explain it → use DP

The trap

Assuming greedy works. Coin Change is the counterexample that ends careers: greedy fails on [1, 3, 4] for target 6, and DP is required. Say the proof out loud before you commit.

The move O(n) time · O(1) space

best = cur = nums[0]               # Kadane's maximum subarray
for x in nums[1:]:
    cur = max(x, cur + x)          # carrying the past, or starting fresh
    best = max(best, cur)
return best

Picking the least-loaded shard for the next record, evicting the cache entry that is cheapest to lose, choosing a compression level per block. Every load balancer is a greedy algorithm you trust because somebody proved the invariant first.

Advanced Graphs

Now the edges have prices.

BFS quietly assumes every road takes one minute. Real roads do not. Dijkstra is BFS with a priority queue instead of a plain queue: always expand the city that is cheapest to reach so far. The first time you settle a city, that is its true cheapest cost.

You reach for it when

  • edges carry weights, costs, times, distances
  • “cheapest” rather than “fewest steps”
  • connect everything as cheaply as possible → MST
  • “did adding this edge make a cycle?” → union-find

The trap

Dijkstra breaks on negative edge weights — that is Bellman-Ford territory. And you must keep the stale-entry continue, or nodes get expanded again after they were already settled.

The move O(E log V) with a heap

import heapq

dist = {start: 0}
pq = [(0, start)]                              # (cost so far, node)
while pq:
    cost, node = heapq.heappop(pq)             # always the cheapest open one
    if cost > dist.get(node, float("inf")):
        continue                               # stale entry, skip it
    for nxt, w in graph[node]:
        if cost + w < dist.get(nxt, float("inf")):
            dist[nxt] = cost + w
            heapq.heappush(pq, (cost + w, nxt))
return dist

Network routing, cost-based query planning, and picking the cheapest region hop for a large data transfer. Union-find — the other tool in this box — is what detects “this merge created a cycle” in dependency graphs and drives Kruskal's minimum spanning tree.

2-D Dynamic Programming

Same idea, one more axis.

When the answer depends on two things — position in string A and position in string B, or index plus remaining budget — one row of boxes is not enough. Use a grid. dp[i][j] means “the answer for the first i of one and the first j of the other”. Fill it in, read the corner.

The move O(m × n) time and space — often reducible to two rows

dp = [[0] * (n + 1) for _ in range(m + 1)]   # +1 row and col for "empty"

            dp[i][j] = dp[i - 1][j - 1] + 1              # match: diagonal + 1

Bit Manipulation

XOR remembers by forgetting.

A number is a row of switches. a ^ a = 0 — XOR a value with itself and it vanishes. So XOR every number in a list where everything appears twice except one: the pairs erase each other and the loner is the only thing left standing. No map, no sorting, no extra memory.

You reach for it when

  • “every element appears twice except one”
  • count the set bits / flip / mask
  • “without using + or -”
  • iterate all subsets with a bitmask

The trap

Python integers never overflow, so there is no natural 32-bit wraparound. In “Sum of Two Integers” you have to mask with & 0xFFFFFFFF and convert back to a signed value yourself.

The move O(n) time · O(1) space

x = 0
for n in nums:
    x ^= n                 # pairs cancel; the odd one out survives

# the five moves worth memorising:
n & (n - 1)                # turn OFF the lowest 1-bit (loop it to count bits)
n & -n                     # isolate the lowest 1-bit
n & (n - 1) == 0           # is n a power of two?
mask & (1 << i)            # is bit i on?
n >> 1                     # divide by two

Where this lives in real code

Feature flags packed into one integer, unix permission bits (chmod 755), Bloom filters, and compact one-hot encodings. n & (n-1) == 0 is the standard power-of-two check in buffer-size validation.
